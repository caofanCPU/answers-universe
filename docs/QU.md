# 随机答题功能指导文档

## 1. 功能目标

当前项目已经有题库总表 `usb`，随机答题功能是在此基础上，按天为用户生成一组“当日题单”。

该功能的目标是：

1. 以“日期”为维度生成题单。
2. 题单默认固定为 `5` 题，数量由服务端环境变量控制。
3. 生成结果优先来自未被历史使用过的题目。
4. 每套题单必须包含且只包含 `1` 道首题。
5. 用户可以通过日历查看任意日期是否已生成题单，并查看当天题单详情。
6. 当题库条件不足时，系统必须给出一次性、完整、可执行的提示，指导用户补题、设首题、调整分类后重新生成。


## 2. 核心数据表

当前设计采用单表：`random_usb`

用于记录“某一天最终保存下来的随机题单明细”。

建议字段如下：

1. `id`
2. `show_date`
   日期字段，仅表示自然日，语义为 `YYYY-MM-DD`
3. `question_id`
   对应 `usb.id`
4. `question_uuid`
5. `as_first`
   冗余保存，便于后续展示和排序
6. `category`
   冗余保存，便于展示和统计
7. `sort_order`
   题单内顺序
8. `createdAt`
9. `updatedAt`

补充约束建议：

1. `question_id` 全局唯一
   含义：一旦某题进入过 `random_usb`，以后永久不能再被随机题单使用
2. `show_date + question_id` 唯一
   作为当天明细去重保护


## 3. 基础业务规则

### 3.1 历史去重规则

只要某道题进入过 `random_usb`，以后永久不能再被随机题单使用。

也就是说，随机题单的候选池为：

1. `usb` 中未删除题目
2. 且 `id` 不在 `random_usb.question_id` 中


### 3.2 每日题单唯一性

同一个 `show_date` 只能有一套最终题单。

但允许用户执行“覆盖重生成”：

1. 前端必须先弹确认框提示用户
2. 确认后，先删除 `random_usb` 中该日期已有记录
3. 再重新执行整套生成流程


### 3.3 目标题目数量

1. 默认目标数量为 `5`
2. 从服务端环境变量读取
3. 前端不可调整


## 4. 生成规则

### 4.1 首题规则

生成题单时，必须先从候选池中选出 `1` 道首题。

首题条件：

1. `as_first = 1`
2. 未被历史使用过

首题属于稀缺题，业务语义上应当是“更有吸引力、更能激发答题欲望”的题目。


### 4.2 普通题规则

首题确定后，再从剩余候选池中筛选普通题。

普通题必须满足：

1. `as_first = 0`
2. 未被历史使用过
3. `category != 首题.category`
4. 普通题之间 `category` 也不能重复

说明：

1. 这里只看主分类 `category`
2. `sub_category` 不参与去重和筛选唯一性约束


### 4.3 顺序规则

1. 首题必须永远排在第 `1` 题
2. 后续普通题按系统选出顺序保存即可
3. 展示时也应保证首题始终排在第一位


### 4.4 随机策略

随机题单使用“伪随机”策略，不追求真随机，优先考虑实现稳定性和查询性能。

允许采用如下思路：

1. 首题池中按稳定规则取一条
2. 普通题池按分类去重后，再按稳定规则取若干条

不要求数据库层面做高成本真随机排序。


## 5. 保存规则

保存接口与页面规则必须保持一致，最终保存条件统一为：

1. 总题数必须等于目标数
   当前默认是 `5`
2. 必须有且只有 `1` 道首题

以下条件不再作为保存接口的硬性校验项：

1. 分类总数单独是否满足

说明：

1. 分类不足本质上会导致“凑不齐总题数”
2. 因此分类问题仍然需要在生成阶段被诊断出来
3. 但最终保存接口只看“总题数”和“首题数量”


## 6. 生成结果的几种情况

### 6.1 完整成功

满足：

1. 总题数 `5/5`
2. 首题 `1/1`

处理：

1. 可以直接保存
2. 保存成功后跳转到该日期的题单详情页


### 6.2 部分结果

满足：

1. 首题存在
2. 普通题也可能有若干条
3. 但总题数不足目标值

处理：

1. 默认不自动落库
2. 返回候选题目列表给前端预览
3. 返回完整提示，指导用户继续补题

补充说明：

1. 部分结果允许存在于“生成预览”阶段
2. 但部分结果不允许进入最终保存
3. 当前统一规则下，保存接口要求总题数满足目标数，因此部分结果只能作为预览和诊断结果存在
4. 用户后续应根据提示补题、补首题、补分类后重新生成，直到满足保存条件


### 6.3 完全失败

例如：

1. 候选池为空
2. 没有可用首题
3. 没有任何可返回结果

处理：

1. 不允许保存
2. 返回明确提示


## 7. 诊断原则

这是本功能最重要的产品规则之一。

### 7.1 生成接口不能挤牙膏式报错

用户点击“生成”后，后端不能只返回单一错误，而必须一次性给出所有阻塞成功生成的原因。

目标是避免这种差体验：

1. 第一次提示“缺首题”
2. 用户补了首题
3. 第二次又提示“分类不够”
4. 用户补了分类
5. 第三次又提示“普通题被错误地标记为首题”

这种链式报错不允许出现。


### 7.2 一次生成请求必须返回完整诊断

也就是说，当用户点击生成时，接口必须同时返回：

1. 当前能生成出的候选题列表
2. 当前距离成功还差什么
3. 用户需要如何修复

这样用户只要按照提示“正确修改”，下一次生成在纯逻辑上就应当一次成功，不应再出现新的、之前未提示的问题。


## 8. 生成接口应返回的信息

生成接口不是简单返回成功/失败，而是返回“诊断 + 候选结果”。

建议至少返回以下结构信息：

### 8.1 题目结果

1. 首题
2. 普通题列表
3. 合并后的候选题单列表


### 8.2 汇总统计

建议返回：

1. `targetTotal`
2. `actualTotal`
3. `targetFirstCount`
4. `actualFirstCount`
5. `targetCategoryCount`
6. `actualCategoryCount`

当前默认目标表现为：

1. 总数 `5/5`
2. 首题 `1/1`
3. 分类数 `5/5`

这是最完美状态，应显示为绿色。

如果缺题，则对应项标红显示，漏出缺口。


### 8.3 原因枚举

建议至少区分以下几类原因：

1. `POOL_EXHAUSTED`
   题库已耗尽
2. `FIRST_QUESTION_MISSING`
   首题不满足
3. `INSUFFICIENT_DISTINCT_CATEGORIES`
   分类数不满足

说明：

1. 分类数不满足会直接影响普通题补齐
2. 但它是生成阶段的诊断原因，不是保存接口的独立硬校验


### 8.4 修复提示

提示语义上不应只报错，而应尽可能指导用户操作，例如：

1. 需要补充未被使用过的普通题
2. 需要补充首题
3. 需要补充新的主分类
4. 需要将某些题修正为非首题

目标是让用户照着提示修正后，下次生成就成功。


## 9. 页面与交互设计

### 9.1 入口形式

第一优先级入口为日历视图。

原因：

1. 用户可以直观看到哪些日期已经生成
2. 用户可以看到总共生成了多少天的题单
3. 用户可以快速切换不同日期查看和操作


### 9.2 日历页需求

日历页应支持：

1. 显示已生成题单的日期
2. 提供总生成天数等统计信息
3. 点击某日期查看详情
4. 对于未生成日期，支持触发生成


### 9.3 日期详情页需求

某一天的题单详情页应支持：

1. 展示该日期最终已保存的题单列表
2. 联表查询并展示题目详情信息
3. 展示统计提示信息

统计提示信息的语义不是数据库状态字段，而是前端根据如下数据计算出的展示状态：

1. 总数 `5/5`
2. 首题 `1/1`
3. 分类数 `5/5`

由这些统计信息决定前端显示为“完整”还是“缺失提示”。


### 9.4 生成交互

用户点击“生成”后：

1. 后端先执行完整诊断
2. 返回候选题单和提示信息
3. 前端展示结果和提示
4. 用户根据提示去 `questions` 中补题、改分类、设首题
5. 用户回来后重新点击生成


### 9.5 重生成交互

如果某日期已经存在题单：

1. 用户点击“重新生成”
2. 前端弹框确认
3. 确认后删除该日期旧记录
4. 再执行新一轮生成


### 9.6 补题后的流程

第一阶段先保持简单：

1. 用户发现提示
2. 去 `questions` 里补题或改题
3. 回来后重新点击生成

当前不做“自动检测是否已补齐”的增强交互。


## 10. 可复用前端资源

当前 `questions` 目录下已有以下可参考能力：

1. 题目列表
2. 题目详情
3. 题目编辑
4. 题目导入
5. 题目工作台中已有的一些预览思路

后续随机题单页面可优先复用：

1. 题目详情展示结构
2. 多题列表展示风格
3. 已有按钮和交互视觉风格


## 11. 推荐实现顺序

### 第一阶段

先打通后端核心能力：

1. `random_usb` 表
2. 生成诊断逻辑
3. 保存逻辑
4. 按日期查询题单详情
5. 已生成日期列表查询


### 第二阶段

完成前端日历页与详情页：

1. 日历视图
2. 日期详情页
3. 生成预览
4. 重生成确认弹框


### 第三阶段

补充体验优化：

1. 更精细的提示文案
2. 统计信息可视化
3. 更多批量辅助操作


## 12. 第一版开发计划

第一版目标：

1. 只做可用版本
2. 前端文案先直接写英文
3. 先不接中文国际化
4. 不追��复杂状态系统
5. 不追求过度 UI 打磨

推荐按下面顺序开发：

### 12.1 第一步：建表与数据层准备

先完成 `random_usb` 表及相关约束，这是整个功能的基础。

需要完成：

1. 新建 `random_usb` 表
2. 补充必要字段：
   `show_date`
   `question_id`
   `question_uuid`
   `as_first`
   `category`
   `sort_order`
   `createdAt`
   `updatedAt`
3. 建立索引和唯一约束
4. 同步 Prisma schema
5. 生成 migration

原因：

1. 后端生成逻辑依赖该表判断历史去重
2. 前端日历页也依赖该表获取已生成日期


### 12.2 第二步：后端接口与生成逻辑

在表完成后，优先完成后端。

第一版后端只做最小闭环，不做复杂诊断系统。

建议先完成这些能力：

1. 获取已生成日期列表接口
2. 按日期获取题单详情接口
3. 生成预览接口
4. 保存接口
5. 覆盖重生成接口

第一版生成逻辑可简化为：

1. 查可用首题
2. 查可用普通题
3. 组装结果
4. 返回简单提示

第一版提示信息只保留最核心两类：

1. `No first question available`
2. `Not enough normal questions available`

同时返回简单统计即可：

1. `Total: x / 5`
2. `First question: x / 1`
3. `Normal questions: x / 4`


### 12.3 第三步：前端页面

后端稳定后，再接前端。

前端第一版建议做两个页面：

1. 日历页
2. 日期详情页

日历页负责：

1. 展示已生成日期
2. 展示总生成天数
3. 点击日期进入详情
4. 对未生成日期触发生成

日期详情页负责：

1. 展示该日期题单
2. 展示统计信息
3. 支持生成预览
4. 支持重新生成

展示层尽量复用现有 `questions` 目录下的详情和列表样式。


### 12.4 第四步：联调与收口

最后进行端到端联调。

需要验证：

1. 空题库时提示是否正确
2. 无首题时提示是否正确
3. 普通题不足时提示是否正确
4. 满足条件时是否能正常保存
5. 重生成时是否真的先删旧记录再重新生成
6. 日历标记和详情展示是否一致


### 12.5 第一版明确不做的内容

为了控制复杂度，第一版先不做：

1. 中文国际化
2. 复杂状态枚举系统
3. 自动检测补题完成
4. 高级日历交互
5. 复杂修复建议文案
6. 过度精细的前端视觉打磨


## 13. 最终设计原则

随机答题功能后续实现必须遵守以下原则：

1. 历史已使用题永久不可复用
2. 每日题单按日期唯一管理，但允许确认后覆盖重生成
3. 首题必须唯一且排第一
4. 普通题必须是非首题，并且分类互不重复
5. 生成接口必须一次性返回完整阻塞原因，不能链式报错
6. 用户按提示正确修改后，再次生成在逻辑上应当一次成功
7. 保存接口与前端规则必须始终一致
