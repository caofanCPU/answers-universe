# 题目工作台说明书

## 一、设计目标

题目工作台不是一个普通的“编辑页 + 预览页”切换界面，而是一套带有明确确认语义的操作流程。

它的核心目标只有两个：

1. 让用户在修改题目前，先理解当前题目的信息状态。
2. 让任何修改都必须经过用户主动确认后，才真正生效。

因此，工作台中的“编辑”和“预览”不是两个平级展示页，而是两个职责不同的工作状态。


## 二、核心语义

### 1. 编辑

编辑态代表草稿。

用户在这里进行修改、补充、调整，但这些内容此时都只是待确认内容，不应被视为最终结果。


### 2. 预览

预览态代表确认视图。

这里不是单纯为了“看一眼排版”，而是为了让用户确认当前展示结果是否正确、是否可以作为最终生效内容。

只有用户在预览态下主动确认并提交，修改才真正生效。


### 3. 提交

提交不是“保存草稿”，而是“确认草稿生效”。

因此，提交动作必须属于预览态，而不属于编辑态。


## 三、单题工作流

单题场景的流程非常明确：

1. 进入编辑态。
2. 用户修改内容，形成草稿。
3. 用户切换到预览态，对草稿结果进行确认。
4. 用户在预览态主动提交。
5. 提交后，草稿正式成为生效结果。

这意味着：

- 编辑态负责产生草稿。
- 预览态负责确认草稿。
- 提交动作必须发生在预览态。


## 四、多题工作流

多题场景来自题目列表，且列表上下文会带入一组 `GroupIds`。

这组数据的意义不是改变单题的确认逻辑，而是为预览态提供连续审阅能力。

多题场景下，工作台仍然遵循“编辑是草稿、预览是确认”的原则，只是在预览阶段增加了跨题引导。


## 五、入口规则

### 1. 从列表点击“编辑”

如果用户从列表点击的是“编辑”，说明他的意图是修改当前题。

因此，工作台应直接进入当前题的编辑态。

这是对用户意图的直接响应，不应强行先进入预览。


### 2. 从列表点击“预览”

如果用户从列表点击的是“预览”，说明他的意图是查看当前题信息。

因此，工作台应直接进入当前题的预览态。


### 3. 单题进入

如果是单题独立处理，则按单题流程工作：

- 进入编辑
- 修改草稿
- 切换预览确认
- 提交生效


## 六、上下题的使用边界

上下题按钮只属于预览态。

它的职责不是帮助用户“连续编辑”，而是帮助用户在多题场景中进行连续审阅和确认引导。

也就是说：

- 当存在 `GroupIds` 时，预览态可以展示“上一题 / 下一题”
- 当用户点击上下题时，进入的是对应题目的预览态
- 不应因为上下题切换而直接进入对应题目的编辑态

这样设计的目的，是保证用户在跨题浏览时，始终先看到目标题目的当前结果，再决定是否需要编辑。


## 七、多题场景下的标准行为

以“从列表点击编辑某一题”为例，标准流程应当是：

1. 用户从列表点击某题的编辑。
2. 当前题直接进入编辑态。
3. 用户修改后切换到预览态进行确认。
4. 预览态中可以看到上下题入口。
5. 用户点击上一题或下一题时，进入对应题目的预览态。
6. 如果用户需要修改该题，再主动切换到编辑态。
7. 修改完成后，再回到预览态确��并提交。

这个过程中，上下题承担的是“审阅引导”职责，而不是“跳过确认直接连改”职责。


## 八、必须坚持的产品原则

题目工作台需要始终坚持以下原则：

1. 编辑态的内容是草稿，不是最终结果。
2. 预览态是确认视图，不是附属展示页。
3. 提交只能发生在预览态。
4. 多题上下切换只能落到预览态。
5. 从列表进入时，要尊重用户点击“编辑”还是“预览”的原始意图。


## 九、最终结论

题目工作台的本质，不是“两个 tab 切来切去”，而是一个带确认闭环的工作流：

`编辑生成草稿 -> 预览确认结果 -> 提交正式生效`

在多题场景下，这个闭环不会改变，只是在预览阶段增加了跨题审阅能力：

`列表进入当前题 -> 预览或编辑 -> 回到预览确认 -> 上下题继续审阅 -> 需要时再进入编辑`

因此，整个工作台的设计重点，始终应放在两件事上：

1. 明确区分“草稿”与“确认结果”。
2. 让用户的跨题操作始终建立在预览确认的基础上。


## 十、导入校验工作台方案补充

### 1. 问题定义

题目导入场景与单题编辑场景不同。

这里的核心问题不是“如何预览一条题目”，而是：

1. 用户需要快速知道到底是哪一条数据、哪一个字段出了问题。
2. 用户需要在当前页面中直接修改错误内容，而不是回到大段 JSON 中盲改。
3. 合法数据不应被非法数据阻塞，系统必须支持部分导入。


### 2. 总体原则

导入校验工作台应当遵循以下原则：

1. 校验结果必须精确到“记录 + 字段”。
2. 错误项必须支持原地编辑。
3. 合法项与待修复项必须分区展示。
4. 待修复区不采用长列表堆叠，而采用单条翻页式卡片工作流。
5. 用户应当可以随时继续校验、继续修复、继续导入合法项。


### 3. 数据约束

对于用户导入或手工输入的 JSON 数据，每条记录都需要带有前端生成的唯一标识，建议命名为 `importId`。

原始输入：

```json
{
  "A": "...",
  "B": "...",
  "C": "..."
}
```

进入工作台后的内部草稿结构：

```json
{
  "importId": "imp_xxx",
  "A": "...",
  "B": "...",
  "C": "..."
}
```

校验失败时，后端返回的结果应保留相同的 `importId`，并给出字段级错误信息，例如：

```json
{
  "importId": "imp_xxx",
  "fieldErrors": {
    "A": "类型错误",
    "B": "范围非法",
    "C": "必填缺失"
  }
}
```

这样前端就可以稳定地把错误结果映射回具体卡片和具体字段。


### 4. 页面结构

导入页仍然保留顶部的 JSON 输入区，用于：

1. 上传 JSON 文件。
2. 手工粘贴 JSON。
3. 触发首次校验。

但校验完成后，页面主体应切换为“导入工作台”，并分为两个区域：

1. `可导入区`
2. `待修复区`

这两个区域可以通过切换按钮在同一位置展示，以保证桌面端与移动端都能保持简洁布局。


### 5. 待修复区的交互方式

待修复区不采用“很多卡片同时铺开”的方式，也不依赖“收起/展开”解决拥挤问题。

更合适的方式是：

1. 一次只展示一张待修复卡片。
2. 通过“上一条 / 下一条”在错误项之间翻页。
3. 页面中心始终聚焦当前正在修复的这一条数据。

卡片顶部展示：

1. 当前是第几条待修复记录，例如 `第 3 / 50 条`
2. 当前记录的 `importId`
3. 当前记录还剩多少个字段错误
4. `上一条` / `下一条` 翻页按钮

这种方式比长列表更适合移动端，也更符合用户逐条修复的心智模型。


### 6. 错误卡片的字段展示方式

每张待修复卡片的核心，不是展示原始 JSON，而是展示“可直接修改的字段编辑框”。

字段展示遵循以下规则：

1. 默认只展示当前记录中校验失败的字段。
2. 每个字段都以输入框形式直接编辑，而不是只读文本。
3. 出错字段的标题右侧显示红色 `*` 标记。
4. 出错字段的输入框使用红色边框。
5. 错误提示文案展示在输入框下方。

说明：

错误提示信息不应只依赖 placeholder 展示。

原因是 placeholder 会在用户输入后消失，无法持续承担错误提示职责。因此，placeholder 可以保留为示例提示，但字段错误信息必须有独立的红色文案区域。


### 7. 字段类型建议

为保证修复效率与移动端体验，字段组件不应全部使用单行 Input，而应按字段特性选择：

1. `question`、`explanation`、`incorrectAnswers` 使用 `textarea`
2. `difficulty`、`category`、`subCategory` 优先使用 `select`
3. `correctAnswerIndex` 使用数字输入框
4. `tags`、`keywords` 可先使用简单文本输入或 `textarea`

这样可以减少用户再次输错的概率，也能降低修复成本。


### 8. 待修复卡片的核心动作

每张待修复卡片只保留最核心的操作：

1. `重新校验本条`
2. `加入可导入区`

交互规则如下：

1. 用户修改当前卡片中的错误字段。
2. 点击 `重新校验本条` 后，系统只校验当前记录。
3. 如果该记录已无字段错误，则红色 `*` 标记全部消失。
4. 此时用户可以点击 `加入可导入区`。
5. 加入后，这条记录从待修复区移出，并进入可导入区。

这样用户就不需要每修改一条都重新全量处理全部数据。


### 9. 可导入区的职责

可导入区用于承接两类数据：

1. 首次校验时已经合法的数据
2. 在待修复区中修正完成后被加入进来的数据

可导入区的目标不是让用户再次编辑，而是让用户确认并导入。

因此，这一区域应当：

1. 清晰展示当前可导入的记录数量
2. 支持统一导入合法项
3. 允许合法数据先行导入，而不被剩余错误项阻塞

这也是导入工作台必须支持“部分导入”的核心体现。


### 10. 顶部按钮的重新定义

原有的 `Reset` 按钮在新方案下语义不够准确，应重新设计。

推荐拆分为两个动作：

1. `新建导入`
2. `载入示例`

其中：

`新建导入` 的作用是：

1. 清空当前导入工作台状态
2. 清空当前校验结果与修复进度
3. 回到初始输入态
4. 恢复示例 JSON

`载入示例` 的作用是：

1. 仅向输入区填充示例 JSON
2. 不承担“重置整个工作台”的职责

这样可以避免把“清空流程”和“填充示例”混在同一个按钮语义中。


### 11. 最终工作流

导入校验工作台的推荐流程如下：

1. 用户上传或粘贴一批 JSON 数据。
2. 前端为每条记录生成 `importId`。
3. 用户点击校验。
4. 系统将数据分为 `可导入区` 与 `待修复区`。
5. 用户可以先导入当前可导入的数据。
6. 用户在待修复区中，通过翻页卡片逐条修复错误字段。
7. 某条修复完成后，将其加入可导入区。
8. 用户继续导入新增的合法项。
9. 未被加入可导入区的数据，默认视为本轮不导入。


### 12. 结论

导入校验工作台不应只是“显示错误汇总”，而应成为一个真正可操作的修复界面。

它的本质不是让用户阅读错误，而是让用户完成两件事：

1. 快速知道哪一条、哪一个字段错了。
2. 在当前位置直接改正，并把修复后的记录送入可导入区。

因此，最终形态应当是：

`顶部 JSON 输入区 -> 校验拆分为可导入区/待修复区 -> 待修复区按单条翻页卡片修复 -> 修好后加入可导入区 -> 合法项随时导入`
