# Workbench

## 目标

`Workbench` 不是单一页面的名字，而是一组围绕题目数据进行确认、修正、提交的工作流设计。

当前工作台包含两类场景：

1. 单题编辑工作台
2. 批量导入工作台

两者共用一套题目表单与题目预览能力，但交互语义不同：

1. 单题编辑强调草稿编辑与提交生效
2. 批量导入强调批次校验、错误修复、批次导入结果反馈


## 一、单题编辑工作台

### 1. 核心语义

单题工作台的核心语义保持不变：

1. 编辑态产生草稿
2. 预览态负责确认
3. 提交使当前草稿正式生效

这意味着：

1. 编辑不等于生效
2. 预览不是附属页，而是确认页
3. 提交动作属于确认闭环，而不是普通保存


### 2. 入口规则

从题目列表进入时，页面应该尊重用户入口意图：

1. 点击 `Edit`，默认进入编辑态
2. 点击 `Preview`，默认进入预览态

多题连续处理时，预览态可以承担跨题审阅职责，但不应把“上下题切换”变成“直接连续编辑”。


### 3. 多题上下切换

当列表上下文提供 `GroupIds` 时：

1. 上一题 / 下一题属于预览态能力
2. 上下切换落点仍然是预览态
3. 用户若需要修改某题，应主动切回编辑态

这样可以保证多题处理时，用户始终先确认当前结果，再决定是否修改。


## 二、批量导入工作台

### 1. 场景定义

导入页不是“贴 JSON 然后直接提交”的简单入口，而是一个批次工作台。

当前实现采用单批次心智：

1. 用户准备一批 JSON 数据
2. 系统对这一批数据执行校验
3. 用户修复当前批次中的错误项
4. 当批次满足导入条件后再执行导入
5. 导入完成后保留本批次统计结果，直到用户主动开启下一轮


### 2. 当前页面结构

导入页分为三个核心区域：

1. 顶部批次状态区
2. JSON 输入与操作区
3. 待修复工作区

其中第二与第三部分围绕同一批次状态协同工作，而不是彼此独立。


### 3. 顶部批次状态区

顶部状态区使用 4 个图标胶囊，代表当前批次的完整进度：

1. `SiteStacked`
   表示本批次 `Total`
2. `SiteBookmarkCheck`
   表示本批次 `Pass`
3. `SiteBookmarkX`
   表示本批次 `Invalid`
4. `SiteDatabaseZap`
   表示本批次 `Imported`

这 4 个数字共同构成一轮导入的结果反馈，不是独立的装饰信息。


### 4. 顶部统计的状态来源

当前实现中，这 4 个数字不是纯展示常量，而是由页面状态驱动：

1. `Total`
   来自当前 JSON 输入内容解析后的条目数量
2. `Pass`
   来自最近一次批量校验后的合法项数量
3. `Invalid`
   来自最近一次批量校验后的错误项数量
4. `Imported`
   来自最近一次导入成功返回的入库数量

因此，顶部状态区代表的是“当前批次会话状态”。


### 5. 顶部操作按钮的分组

导入页顶部共有 4 个操作按钮：

1. `Upload`
2. `Reset`
3. `Check`
4. `Import`

它们按语义被分成两组：

1. 准备数据
   `Upload`、`Reset`
2. 执行主流程
   `Check`、`Import`

布局原则如下：

1. 移动端采用两列网格，四个按钮尺寸统一
2. 桌面端采用居中双分组布局，中间用轻分隔线区分
3. 四个按钮使用统一尺寸体系，避免因文案长短不同导致大小不一
4. `Check` 与 `Import` 都属于主功能按钮，使用同级主按钮样式
5. `Upload` 与 `Reset` 使用次一级按钮样式


### 6. JSON 输入区

JSON 输入区承担以下职责：

1. 允许上传 JSON 文件
2. 允许直接粘贴或手工编辑 JSON
3. 作为当前批次的原始数据源

这里不是一次性输入框，而是工作台的源数据区域。

任何对 JSON 内容的修改，都会被视为“开启新的批次”或“重置当前批次”。


### 7. 校验机制

点击 `Check` 后，系统会：

1. 解析当前 JSON
2. 为每条记录补齐内部使用的 `importId`
3. 执行批量校验
4. 回写合法与非法项状态

当前导入规则是：

1. 只有全部校验通过后，才允许点击 `Import`
2. 只要仍有 `Invalid`，导入按钮就保持禁用

因此，当前导入工作流是“全量先过检，再允许入库”，而不是“边修边导”。


### 8. 待修复工作区

当批次中存在错误项时，页面会显示 `To Fix` 工作区。

当前实现不是错误列表堆叠，而是单条聚焦式工作流：

1. 一次只展示一条当前待修复记录
2. 通过上一条 / 下一条切换错误项
3. 用户在卡片内直接修改字段
4. 可对当前项单独重新校验
5. 可移除当前错误项

这样可以在移动端和桌面端都保持较好的聚焦体验。


### 9. 共用表单

单题编辑与导入修复共用同一套题目表单组件。

当前表单规则与后端保持一致：

1. `question` 必填
2. `answers` 必填
3. `explanation` 必填
4. `category` 必填
5. `difficulty` 现在为选填，默认值为 `unknown`

共用表单的价值在于：

1. 导入修复与单题编辑使用同一字段结构
2. 字段规则一致，减少两套表单逻辑漂移
3. 新字段或规则变更时，只需要统一调整


### 10. difficulty 规则

`difficulty` 已从必填改为选填，并增加 `unknown` 作为默认值。

当前规则：

1. 表单默认值为 `unknown`
2. 导入时如果缺失 `difficulty`，自动归为 `unknown`
3. 只有当用户显式传入非法 difficulty 值时，才会报校验错误
4. 数据库字段默认值为 `unknown`
5. 数据库约束允许：
   `unknown`, `easy`, `medium`, `hard`

这条规则在以下层面保持一致：

1. 前端表单
2. 导入校验
3. API schema
4. Prisma schema
5. 初始化 SQL


### 11. 导入成功后的交互

由于当前产品规则是“全部校验通过后才允许导入”，所以导入成功通常意味着本轮批次已经完成。

当前成功交互设计如下：

1. 点击 `Import`
2. 成功后弹出成功弹窗
3. 弹窗明确展示本轮成功入库数量
4. 顶部 `Imported` 图标数字同步更新
5. 页面进入“本轮已完成态”

这里的“已完成态”非常关键：

1. `Check` 被禁用
2. `Import` 被禁用
3. 顶部统计结果保留
4. 用户仍可查看本轮结果
5. 但不能对同一批次重复执行导入

这样可以在前端层面降低重复操作导致垃圾数据的风险。


### 12. 导入失败后的交互

导入失败或校验请求失败时，不再使用页面内联红框提示，而是统一使用错误弹窗。

当前规则：

1. 请求错误通过弹窗反馈
2. 弹窗用于承载错误原因
3. 失败不会强制清空当前批次数据
4. 用户可以继续修正或重试


### 13. 新一轮批次的开始条件

当前页面不会在导入成功后自动清空数据。

原因是：

1. 顶部 4 个统计项要保留本轮完整结果
2. 用户需要看到这一轮到底导入了多少、通过多少、落库多少

但只要用户执行以下任一动作，就视为开启新一轮批次：

1. 上传新的 JSON 文件
2. 点击 `Reset`
3. 手动修改 JSON 输入框内容

一旦进入新一轮，页面会执行统一重置：

1. 清空已校验状态
2. 清空本轮导入结果
3. 清空本轮完成态锁定
4. 顶部统计回到新批次对应的数据状态


### 14. Reset 的语义

当前 `Reset` 的语义不是“仅清空错误”，而是：

1. 载入示例 JSON
2. 同时重置当前批次状态

因此它本质上是“以示例数据开启一轮新批次”。


### 15. 页面与状态的一致性原则

导入工作台需要始终保证以下一致性：

1. 顶部状态区与当前批次状态一致
2. JSON 输入区与当前批次数据源一致
3. 待修复区与当前错误项集合一致
4. 成功弹窗与当前批次导入结果一致
5. 按钮可用性与当前批次阶段一致

换句话说，页面不是松散的几个区域拼接，而是围绕“当前批次会话”联动。


## 三、设计原则总结

当前 Workbench 设计遵循以下原则：

1. 单题编辑与批量导入是两类不同工作流，不应混用语义
2. 单题编辑强调草稿、预览、确认闭环
3. 批量导入强调批次状态、错误修复、结果反馈闭环
4. 状态反馈必须和真实代码状态一致，不能停留在概念方案层
5. 按钮层级、图标语义、弹窗反馈都必须服务于当前任务阶段


## 四、当前结论

当前系统中，题目工作台已经形成两个稳定方向：

1. 单题工作台：
   `编辑产生草稿 -> 预览确认 -> 提交生效`
2. 导入工作台：
   `准备一批 JSON -> 批量校验 -> 修复错误 -> 全量通过后导入 -> 保留本轮统计 -> 用户主动开启下一轮`

这份文档的目的不是描述理想方案，而是记录当前已经落地并应继续保持一致的设计。
