# 题目工作台说明书

## 一、设计目标

题目工作台不是一个普通的“编辑页 + 预览页”切换界面，而是一套带有明确确认语义的操作流程。

它的核心目标只有两个：

1. 让用户在修改题目前，先理解当前题目的信息状态。
2. 让任何修改都必须经过用户主动确认后，才真正生效。

因此，工作台中的“编辑”和“预览”不是两个平级展示页，而是两个职责不同的工作状态。


## 二、核心语义

### 1. 编辑

编辑态代表草稿。

用户在这里进行修改、补充、调整，但这些内容此时都只是待确认内容，不应被视为最终结果。


### 2. 预览

预览态代表确认视图。

这里不是单纯为了“看一眼排版”，而是为了让用户确认当前展示结果是否正确、是否可以作为最终生效内容。

只有用户在预览态下主动确认并提交，修改才真正生效。


### 3. 提交

提交不是“保存草稿”，而是“确认草稿生效”。

因此，提交动作必须属于预览态，而不属于编辑态。


## 三、单题工作流

单题场景的流程非常明确：

1. 进入编辑态。
2. 用户修改内容，形成草稿。
3. 用户切换到预览态，对草稿结果进行确认。
4. 用户在预览态主动提交。
5. 提交后，草稿正式成为生效结果。

这意味着：

- 编辑态负责产生草稿。
- 预览态负责确认草稿。
- 提交动作必须发生在预览态。


## 四、多题工作流

多题场景来自题目列表，且列表上下文会带入一组 `GroupIds`。

这组数据的意义不是改变单题的确认逻辑，而是为预览态提供连续审阅能力。

多题场景下，工作台仍然遵循“编辑是草稿、预览是确认”的原则，只是在预览阶段增加了跨题引导。


## 五、入口规则

### 1. 从列表点击“编辑”

如果用户从列表点击的是“编辑”，说明他的意图是修改当前题。

因此，工作台应直接进入当前题的编辑态。

这是对用户意图的直接响应，不应强行先进入预览。


### 2. 从列表点击“预览”

如果用户从列表点击的是“预览”，说明他的意图是查看当前题信息。

因此，工作台应直接进入当前题的预览态。


### 3. 单题进入

如果是单题独立处理，则按单题流程工作：

- 进入编辑
- 修改草稿
- 切换预览确认
- 提交生效


## 六、上下题的使用边界

上下题按钮只属于预览态。

它的职责不是帮助用户“连续编辑”，而是帮助用户在多题场景中进行连续审阅和确认引导。

也就是说：

- 当存在 `GroupIds` 时，预览态可以展示“上一题 / 下一题”
- 当用户点击上下题时，进入的是对应题目的预览态
- 不应因为上下题切换而直接进入对应题目的编辑态

这样设计的目的，是保证用户在跨题浏览时，始终先看到目标题目的当前结果，再决定是否需要编辑。


## 七、多题场景下的标准行为

以“从列表点击编辑某一题”为例，标准流程应当是：

1. 用户从列表点击某题的编辑。
2. 当前题直接进入编辑态。
3. 用户修改后切换到预览态进行确认。
4. 预览态中可以看到上下题入口。
5. 用户点击上一题或下一题时，进入对应题目的预览态。
6. 如果用户需要修改该题，再主动切换到编辑态。
7. 修改完成后，再回到预览态确��并提交。

这个过程中，上下题承担的是“审阅引导”职责，而不是“跳过确认直接连改”职责。


## 八、必须坚持的产品原则

题目工作台需要始终坚持以下原则：

1. 编辑态的内容是草稿，不是最终结果。
2. 预览态是确认视图，不是附属展示页。
3. 提交只能发生在预览态。
4. 多题上下切换只能落到预览态。
5. 从列表进入时，要尊重用户点击“编辑”还是“预览”的原始意图。


## 九、最终结论

题目工作台的本质，不是“两个 tab 切来切去”，而是一个带确认闭环的工作流：

`编辑生成草稿 -> 预览确认结果 -> 提交正式生效`

在多题场景下，这个闭环不会改变，只是在预览阶段增加了跨题审阅能力：

`列表进入当前题 -> 预览或编辑 -> 回到预览确认 -> 上下题继续审阅 -> 需要时再进入编辑`

因此，整个工作台的设计重点，始终应放在两件事上：

1. 明确区分“草稿”与“确认结果”。
2. 让用户的跨题操作始终建立在预览确认的基础上。
