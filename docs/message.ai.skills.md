# Message AI Skills

## 一、用途

这份文档不是面向某个具体页面，也不是面向某个具体项目结构。

它的目标是给 AI 或协作者一套通用执行规则，用于处理网站项目中的国际化消息改造任务。

重点不是“翻译内容写什么”，而是：

1. 先判断该不该改代码。
2. 先判断消息应放在哪里。
3. 先判断应该改页面层、builder 层，还是组件层。
4. 尽量把多语言扩展变成纯消息文件工作。


## 二、核心原则

### 1. 优先消除代码中的语言分支

如果组件中存在类似：

```ts
locale === 'xx'
isZh ? '...' : '...'
```

应优先把这些分支移出组件。

目标是：

1. 组件不直接判断语言。
2. 文案不写死在组件逻辑中。
3. 语言切换不影响组件行为代码。


### 2. 页面层负责取翻译

优先在服务端页面层或路由层获取翻译，再把结构化文案对象传给客户端组件。

不要优先选择：

1. 深层组件自己取翻译。
2. 在多个组件中重复写 `t('...')`。
3. 让共享组件依赖某个具体的翻译框架 API。


### 3. 用 builder 作为缓冲层

当一个页面或一组组件需要较多翻译字段时，应引入 builder 或 copy adapter。

例如：

1. `buildFormCopy`
2. `buildListCopy`
3. `buildDetailCopy`
4. `buildImportCopy`

builder 的意义是：

1. 控制消息字段扩散。
2. 把页面层和组件层解耦。
3. 让消息结构调整集中在一个地方发生。


## 三、AI 执行顺序

### 第一步：先查消息入口

开始改造前，先确认项目的国际化入口：

1. 消息从哪里加载。
2. 是否支持多文件合并。
3. 当前消息文件是单文件还是分模块。
4. 页面层是否已经有服务端取翻译的能力。

如果入口已经支持合并，不要重新设计整套 i18n。


### 第二步：搜索硬编码与语言分支

优先搜索：

1. `isZh`
2. `locale ===`
3. `? '中文' : 'English'`
4. 明显的页面按钮、提示语、状态文案硬编码

先确定改造范围，再决定分几步处理。


### 第三步：识别共享消息块

如果多个页面共用同一个表单、详情组件、工作台、列表项组件，应优先识别共享消息块。

常见共享块包括：

1. 表单字段文案
2. 详情展示文案
3. 列表项按钮文案
4. 预览区文案
5. 导入或工作台工具栏文案

共享块应尽量单独建 copy 类型，而不是散在多个页面里。


### 第四步：页面消息与共享消息分离

组织消息时，优先分成两类：

1. 页面专属消息
2. 共享组件消息

页面专属消息通常包括：

1. 页面标题
2. 页面描述
3. 页面顶部操作按钮
4. 页面级状态提示

共享组件消息通常包括：

1. form 字段名
2. preview 区块文案
3. detail 区块文案
4. list item 按钮文案


### 第五步：先改英文链路

如果项目还在快速开发期，优先只把主语言链路收好。

此阶段重点是：

1. 统一消息组织方式
2. 清理组件中的语言判断
3. 把 copy / builder / 页面层调用打通

不要在这个阶段急着铺很多语言。


### 第六步：最后再扩语言

当消息结构稳定后，再新增其他语言文件。

理想状态下，这一步不应该再需要修改业务代码，只需要：

1. 新增语言消息文件
2. 保持相同 key 结构
3. 做翻译与校验


## 四、消息文件组织建议

### 1. 不要过度集中

如果所有消息都堆在一个超大 JSON 文件里，AI 和人工维护成本都会明显上升。

建议将：

1. 基础消息
2. 业务消息

分开管理。


### 2. 不要过度碎片化

也不要把每个页面都拆成一个独立文件，除非项目非常大。

更稳妥的做法是按功能块拆，例如：

1. `common`
2. `dashboard`
3. `questions`
4. `pricing`

或者按业务域拆分。


### 3. 层级不要过深

消息结构只需要达到“能清晰定位”的程度即可。

不要为了结构整齐把层级做得过深，否则：

1. key 路径冗长
2. 修改成本高
3. 页面调整时容易牵一发而动全身


## 五、组件改造规则

### 1. 共享组件不关心翻译来源

共享组件只接收结构化文案对象，不关心：

1. 文案来自哪个文件
2. 文案来自哪个 namespace
3. 使用的翻译框架是什么


### 2. 组件 props 只接收自己需要的最小文案集

不要把整棵翻译树直接传进组件。

应该只传：

1. 当前组件真正需要的字段
2. 结构清晰、职责单一的 copy 对象


### 3. 新增文案时先判断该放哪一层

遇到一个新文案，不要立刻加到任意 JSON 里。

应先判断：

1. 这是页面独有的吗
2. 这是共享组件要复用的吗
3. 这会不会影响多个页面

先判断归属，再决定消息位置。


## 六、AI 常见错误

### 1. 只改一半

常见错误是：

1. 页面已经改成翻译
2. 组件内部仍保留 `isZh`

这会形成双轨制，后续更难维护。


### 2. 直接在深层组件调用翻译 API

这会让组件和翻译框架绑定，降低复用性。


### 3. 为了灵活暴露过多参数

国际化层的 builder 和 copy 类型应追求清晰，不应为了“未来可能会用”暴露大量无意义字段。

应坚持：

1. 少而明确
2. 只传当前真正需要的消息
3. 缺了再加，不要预埋过多无效参数


### 4. 新语言扩展时顺手改业务代码

如果新增语言时还需要改很多业务代码，通常说明第一阶段的国际化架构没有收干净。


## 七、推荐交付标准

当 AI 完成一轮国际化改造后，至少应满足：

1. 目标组件中不再存在基于语言的条件分支。
2. 页面层统一负责取翻译。
3. 共享组件只接收结构化 copy。
4. 新增语言时原则上只需要补消息文件。
5. 类型检查通过。


## 八、最终判断标准

一套国际化改造是否做对，不看“是不是把文案都挪进 JSON 了”，而看这三件事：

1. 代码里是否还散落语言判断。
2. 消息结构是否稳定且可维护。
3. 后续扩语言时是否可以基本不动业务代码。

如果这三点成立，这套改造就是成功的。
